# mcp-eval — design

Status: approved 2026-08-04

Implementation status: Phase 1 is implemented. This document also describes later
phases; where an older example conflicts with the Phase 1 privacy boundary below, the
implemented Phase 1 behavior governs.

## Problem

Agents are the primary consumers of MCP servers, and nothing measures what a server
costs them. Server authors see request counts and error rates. What an agent actually
pays is turns spent diagnosing, dead ends taken, schemas guessed at, and work redone
after a call reported success and changed nothing.

Those costs are invisible today, so they never get fixed. A day of browser automation
work can run 85% diagnosis and 15% task, and the transcript of that day is the only
record — unstructured, unquantified, and gone at the end of the session.

## Goals

1. Capture, objectively and automatically, what MCP servers cost agents.
2. Separate persistent defects from one-off flakes with math, not impression.
3. Hand development agents findings they can act on, each with a probe that proves the
   fix landed.
4. Work against any MCP server, including ones we do not own and cannot change.

## Non-goals

- Not an uptime monitor. Server-side health is already measured elsewhere.
- Not a conformance suite. Spec compliance is table stakes; this measures usability.
- Not a benchmark leaderboard. Comparability across servers is a side effect, not the
  point.

## Architecture

Five units, each with one purpose and a defined interface.

| Unit | Purpose | Interface |
| --- | --- | --- |
| `shim` | Passthrough proxy in front of a server; frames every JSON-RPC message; redacts at capture | `mcpeval shim -- <server cmd>` |
| `store` | Append-only event log plus query index | `~/.mcp-eval/store/` |
| `promoter` | Rolls calls into issues; scores; promotes to findings | `mcpeval promote` |
| `prober` | Capability battery; writes the same records as real calls | `mcpeval probe --server X` |
| `reporter` | Ranked briefs, generated verification probes, lifecycle | `mcpeval findings --format agent\|md\|json` |

Data flows one way: shim and prober write to store, promoter reads store and writes
findings, reporter reads findings. No unit reaches backwards.

### Transport coverage

- **stdio servers**: the shim wraps the server command in the client's MCP config. Full
  fidelity.
- **HTTP/SSE servers**: the shim runs as a local reverse proxy; the config points at it.
  Full fidelity.
- **In-process servers** (some first-party integrations cannot be fronted at all):
  annotations plus transcript import. Latency is coarse and call ordering is
  best-effort, but the record schema is identical, so findings from these servers rank
  alongside the rest with a lower confidence weight.

The shim structurally classifies JSON-RPC only for safe accounting; it never changes the
proxied bytes. Malformed JSON and syntactically valid JSON that is not a JSON-RPC 2.0
request, notification, or response are forwarded untouched and recorded as `unparsed`.

## Data model

Three record types, one JSONL file per day, indexed into SQLite for query.

### `call`

```
{ "ts": "...", "session": "session:<sha256>", "seq": 412,
  "server": "bobby-browser", "method": "tools/call", "tool": "click",
  "args": { "shape": { "sessionId": "uuid", "pageId": "uuid",
                       "target": { "role": "enum:button", "accessibleName": "str<32",
                                   "ordinal": "int" } } },
  "latency_ms": 812, "outcome": "error",
  "error": { "code": "str<32", "layer": "str<8", "retryable": false,
             "template": "{message}" }, "shim_self_us": 84, "kind": "real" }
```

Phase 1 derives `windows` in SQLite during `mcpeval index`: the five preceding and three
following physical call rows within the same session. The JSONL call is never held open.
Sequence is what reproduces a defect and what makes a suboptimal documented path
visible; neither is recoverable from an isolated failure.

### `annotation`

```
{ "type": "annotation", "ts": "...", "call": "<call-id>", "author": "agent",
  "kind": "blocked-optimal-path" | "undocumented-behavior" | "false-success"
        | "instruction-divergence" | "workaround",
  "note": "<= 240 chars, no payload content" }
```

The only channel for things a transport log cannot see. Kept short and typed so it
aggregates.

### `probe_run`

```
{ "type": "probe_run", "ts": "...", "server": "...", "probe": "degradation-over-n",
  "result": "fail", "measurement": { "actions_before_first_failure": 6 },
  "finding": "<finding-id or null>" }
```

## Redaction

Redaction happens in the shim, before anything is written. There is no verbose mode and
no raw buffer, so there is no dangerous switch to leave on.

**Recorded**: argument keys; value types; string length buckets; array and object sizes;
enum values (the server's own schema supplied them, so they carry no user content);
numeric and boolean scalars; the registrable domain of URLs with path, query and
fragment dropped; whether a filesystem path resolved inside a declared allowed root, and
its depth.

**Never recorded**: free text of any kind, with one deliberate exception (an
annotation's `note`, below); file paths; query strings; header values; anything from a
field whose schema type is an unbounded string, unless that field's schema declares an
enum.

**Error messages** are reduced to the constant `{message}`, plus `template_id`: a
salted, non-invertible fingerprint — the first 8 bytes of
`SHA256(salt || 0x00 || skeleton(message))`, lowercase hex — where `skeleton` collapses
UUIDs, quoted runs, `scheme://` runs, absolute paths, and digit runs out of the message
first. Neither the raw message nor its skeleton is ever stored; `template_id` exists
only so two failures sharing a defect can be told apart from two unrelated ones, which
the constant `{message}` alone cannot do since it collapses every distinct defect into
one bucket. String error codes, layers, and kinds become length buckets, except a string
code that satisfies the identifier grammar (non-empty, ASCII, starts with a letter,
`[A-Za-z0-9_.:-]*` afterward, at most 64 bytes) — those are symbolic labels rather than
prose and are kept verbatim. Scalar numeric and boolean codes may remain.

Identifier metadata also has an enforced boundary. Session values become stable SHA-256
tokens. Server labels and JSON-RPC methods use bounded ASCII label grammars. A tool name
is retained whenever it satisfies the bounded tool-name grammar (non-empty, ASCII
alphanumeric plus `_`, `-`, `.`, or `:`, at most 128 bytes) — whether or not
`tools/list` ever declared it, so servers that load schemas on demand still get a usable
tool dimension. A prose-shaped name (spaces, slashes, and the like) uses `unlisted`
instead. Store serialization applies a second validation pass so directly constructed
records cannot write path-, query-, or free-text-shaped identifiers.

The one deliberate exception to "no free text": an `annotation` record's `note` field,
bounded to 240 characters and scrubbed of control characters (see the `annotation`
record type below), written to `annotations-*.jsonl` alongside the `calls-*.jsonl`
journal. Every other field, in every record type, is structured and content-free.

Consequence, accepted: a stored failure says "a 4KB string in field `value` failed
validation", never what the string was. `calls-*.jsonl` is safe to hand to a development
agent or attach to an upstream issue with no review step. `annotations-*.jsonl` is not:
`note` is agent-authored prose that automated redaction cannot vouch for, so
`mcpeval doctor --check-redaction` counts how many notes are present and asks for a
human pass over them before that file is shared.

The salt that makes `template_id` non-invertible is generated once per install and
stored at `<MCPEVAL_HOME>/.salt` — a dotfile sibling of `store/`, deliberately outside
it. Only `store/` is shareable; the salt must never accompany it. The skeleton space of
MCP error messages is small and guessable, so salt plus journal would let someone
recover which messages produced which fingerprint.

## Promotion

An **issue** is the aggregation key `(server, tool, error-template)`. A **finding** is an
issue that cleared promotion.

```
rate        = failures / calls for the issue
confidence  = Wilson lower bound (95%) of rate      # 2-of-2 must not outrank 40-of-100
recency     = 0.5 ^ (days_since_last_occurrence / 14)
cost        = median agent turns burned inside the failure windows for this issue
blast       = distinct tools appearing in those windows
score       = confidence * recency * log2(1 + cost) * (1 + log2(blast))
```

Promotes when `score >= threshold` **and** the issue appears in at least two distinct
sessions. The two-session rule is what keeps a single bad afternoon from minting
findings.

`threshold` starts at 0.15 and is calibrated once in phase 2 against the seed corpus:
the value is correct when every blocker from that corpus promotes and no
single-occurrence annoyance does. It is a config value, not a constant in code.

Severity is derived, not scored: `false-success` and `blocked-optimal-path` annotations
promote an issue one severity band regardless of rate, because an agent that trusts a
false success produces wrong work rather than slow work — the day this design came from
included a false success that caused a real-world side effect.

## Probe battery

Probes exercise a server and write the same `call` records as real work, tagged
synthetic. They fill the journal; the journal is what carries weight.

Safety: probes are read-only by default against every server. Mutating probes run only
against targets a server author declares in a `mcp-eval.manifest.json` sandbox block.
A server with no manifest is never mutated.

| Probe | Measures |
| --- | --- |
| `discovery-cost` | `tools/list` bytes, token estimate, share of context budget, time to first callable tool, round-trips when schemas are deferred |
| `schema-guessability` | Whether a well-formed naive call succeeds; required-vs-default coverage; enum presence; casing consistency between envelope and body; unknown-field strictness |
| `error-honesty` | Code stability; whether `retryable: true` errors ever succeed on retry; whether the message names the remedy |
| `state-recovery` | Session survival across idle; whether one failed call leaves the session usable; whether any tool re-establishes a broken dependency |
| `contention` | Two clients against one server: exclusive ports, single-session resources, squatted locks |
| `degradation-over-n` | The same action repeated until first failure. Static suites never find this class |
| `instruction-fidelity` | LLM-judged: follow each tool description literally, flag divergence between documented and actual behavior |

The last two are the ones nobody builds, and they are where the hardest blockers of the
seed corpus live.

## Metrics

Reported in agent-cost units, because that is the currency being spent.

- turns-to-first-success, per task type
- tokens-to-first-success
- dead-end rate: calls producing no progress
- workaround depth: alternate routes attempted before one worked
- schema round-trips before first valid call
- latency p50 / p95 per tool

## Output contract

`mcpeval findings --format agent` emits, per finding: what breaks, the shape-level
repro, the cost in agent turns, blast radius, severity, and a generated probe that fails
today.

Lifecycle: `open` → `fix-claimed` (probe exists and fails) → `verifying` (probe passes)
→ `closed` (probe green across three consecutive runs). A finding whose probe goes red
again reopens automatically with its history intact.

Findings that no probe can express — an unclear tool description, a missing concept in
the docs — carry `probe: null`, are capped at severity `medium`, and close by hand. They
are expected to be the minority; if they are not, the probe generator needs work.

## Seed corpus

The store starts populated. One day of browser-automation work across four servers
produced seventeen observations:

| Category | n | Representative |
| --- | --- | --- |
| False success | 2 | A click reported success with no dialog open, so the following input went to the wrong window and caused a real side effect. A second returned `completed` with element evidence and changed nothing. |
| Error opacity | 3 | One generic interface error mapped to three distinct causes in a single session, with no correlation id and no pointer to a log. |
| Degradation over N | 1 | A content channel failed permanently after five to seven actions on a page; a fresh page reset it. |
| Recovery gaps | 2 | No tool-surface way to re-establish a dependency after restart; the working procedure was found by reading the server's source. |
| Contention | 1 | Two runtimes configured for one exclusive port; the idle one squatted it and every session creation failed. |
| Schema guessability | 3 | camelCase envelope wrapping a snake_case body; required fields with no defaults. Four failed calls before the first valid one. |
| Undiscoverable constraint | 2 | A file-upload call rejected paths with a message that never stated which roots were allowed. |
| Harness friction | 3 | Deferred-tool round-trips; one server's `tools/list` consuming 99% of the advertised budget; silent working-directory resets between shell calls. |

These are entered as annotations against reconstructed call records, flagged
`retroactive`, and carry the same lower confidence weight as transcript-imported data.

## Rollout

Each phase is useful on its own.

1. **shim + store**, one server. Capture only, no analysis. Proves redaction correctness
   and measures shim overhead.
2. **promoter + reporter**. Findings emerge from data already collected.
3. **probe battery**, including `degradation-over-n` and `instruction-fidelity`.
4. **Self-closing loop**, then additional servers including third-party ones.

## Testing

- Shim: golden-file tests over recorded JSON-RPC sessions; a redaction test asserting
  that a fixture containing planted secrets produces a store with none of them present.
  Overhead budget: p95 under 2ms added per call.
- Promoter: property tests on the scoring function — monotonic in rate, decreasing in
  age, and never promoting a single-session issue.
- Prober: each probe runs against a deliberately broken fixture server that exhibits the
  defect the probe hunts, and against a clean one.
- Reporter: lifecycle transitions, including reopen-on-regression.

## Risks

- **Shim overhead becomes the thing being measured.** Mitigated by the 2ms p95 budget
  and by recording shim self-time in each record so it can be subtracted.
- **The store grows without bound.** Daily files, compaction after 90 days into
  per-issue aggregates; raw call records are not needed once an issue is established.
- **Findings become a wish list.** The self-closing lifecycle is the defense: a finding
  that cannot be expressed as a probe is capped at medium severity, which keeps the top
  of the list actionable.
- **Annotation discipline decays.** Accepted. The quantitative spine does not depend on
  annotations; they enrich findings rather than create them.

## Deliverables

1. `mcpeval` CLI — the five units above.
2. A thin plugin wrapper: a skill teaching the annotation workflow and when to write
   one, plus slash commands for `probe`, `findings`, and `promote`.
3. `mcp-eval.manifest.json` schema, so a server author can declare sandbox targets and
   opt into the deeper battery.
